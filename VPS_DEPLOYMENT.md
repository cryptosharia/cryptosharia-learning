# VPS staging deployment

Build from the reviewed commit: `docker build -t cryptosharia-learning:staging-$(git rev-parse --short HEAD) .`. Replace the Compose image tag with that SHA tag before deploying. Create the external `cryptosharia_proxy` network separately and proxy HTTPS to `cryptosharia-learning-staging:3000` via Nginx Proxy Manager. Provide `ORIGIN`, `API_BASE_URL`, and `API_KEY` in a protected `.env.staging` file. Health checks liveness only.

The app uses static public configuration at build time: `PUBLIC_ACADEMY_BACKEND`, `PUBLIC_ACADEMY_ENABLED`, `PUBLIC_FIREBASE_MODE`, `PUBLIC_FIREBASE_API_KEY`, `PUBLIC_FIREBASE_AUTH_DOMAIN`, `PUBLIC_FIREBASE_PROJECT_ID`, `PUBLIC_FIREBASE_MESSAGING_SENDER_ID`, `PUBLIC_FIREBASE_APP_ID`, `PUBLIC_FIREBASE_AUTH_EMULATOR_URL`, `PUBLIC_FIREBASE_FIRESTORE_EMULATOR_URL`. These are public, never secrets. Pass any required values as `docker build --build-arg PUBLIC_NAME=value` for the listed public names. These values are embedded in the client bundle and image; never pass secrets as build arguments. Do not put credentials in the build context.

The API backend is still required in API mode. The current API URL policy only permits loopback or the pinned production origin when `VERCEL_ENV=production`, so VPS staging needs a separately reviewed API policy before API functionality works; do not set production mode merely to bypass it. Firebase is used for local emulator mode and live Firebase is deliberately rejected in this standalone application. Supabase and Vercel Blob are not direct dependencies. Data and API migration remain separate blockers. The project declares Node 24, so compatibility with the requested Node 22 image needs validation. The default adapter remains Vercel; `ADAPTER=node npm run build` selects Node.
